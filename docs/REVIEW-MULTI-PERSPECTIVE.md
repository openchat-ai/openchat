# 十二人谈 OpenChat — 项目多视角审查记录

> 2026-05-16，一次持续 6 小时的项目定位讨论。以下为各角色发言摘要。

---

## 1. 苛刻的审查者 — "你们的自嗨式描述从未面对过真实的技术难度"

实际存在的、能跑的东西：
- P2P 通信（~1500 行，可用）
- 语音编解码（~2000 行，可用）
- P2P 聊天（~5000 行，可用）
- Agent Console（~3000 行，半成品）

画饼的部分：
- NeuralBrain — 64→32→8 玩具，比 1990 年的 MNIST 分类器还小
- NeuralMesh — 把几十个浮点数 P2P 广播取平均，不是分布式训练
- EvolutionEngine — 字符串匹配判断成败，if-else 规则引擎

定位要么做 P2P 隐私聊天 + 本地 AI 助手（代码现成），要么放弃。

---

## 2. GitHub 开源贡献者 — "实际项目 A 和想象中的项目 B 被写在同一个 README 里"

真正打动人的部分：
- 语音系统做得真认真（RNNoise + 编解码器）
- P2P 网络层写得扎实
- fairy-guardian 工业可用
- 部署系统完整（含 riscv64）

建议：把项目 A 的 README 写好，把项目 B 从 README 里删掉。想搞分布式大模型就去 fork Petals，把 fairy-guardian 的模型服务器守护接进去。

---

## 3. 干了大半年的核心工程师 — "真正扛起这个项目的代码，在你根本不提的地方"

每个 commit 写的都是"增强自进化能力""优化神经网格"，但真正有工程密度的代码在语音系统和 P2P 网络层。

三个方案：
- 方案一：fork Petals，把 P2P 层嫁接到它的分布式训练上
- 方案二：放弃大模型叙事，定位为隐私 P2P 语音通讯 + 本地 LLM
- 方案三：做底座——P2P 通信中间件 + 模型服务器守护，独立 SDK 发布

---

## 4. Petals 核心开发者 — "你的代码里没有分布式大模型"

技术评审：
- `neural-mesh.js` 的合并算法是 FedAvg（2017），没错。但没有模型版本协商、初始化种子同步、数据分布校准——分布式训练的第一性原理级问题
- `neural-brain.js` 的 64→32→8 架构，即使 10000 个节点跑，也学不会比"这个句子长不长"更复杂的东西——模型容量本身就是瓶颈

真正的优势：P2P 打洞、NAT 穿越、容错重连——这些才是分布式系统最难的部分，openchat 已经做了。

建议：删掉 toy NN，把 P2P 传输层做成 SDK，给 Petals 提 PR。

## 6. VC 尽调分析师 — "不投，但跑道没花完"

严重风险：
- 叙事与代码严重脱节——是两个不同的产品被塞进了同一个 Git 仓库
- 技术叙事抄袭了赛道头部项目但不是 fork/集成/合作
- `neural-mesh.js` 154 行核心 for 循环，不是生产级系统

有价值的资产：
- 语音系统（技术壁垒，104x 压缩 <1ms）
- P2P 网络层（代码质量中上）
- fairy-guardian（完成度 100% 的模块，独立运营可能）

估值：对标"分布式大模型"→ 零。对标"P2P 实时通讯基础设施"→ 种子轮可考虑。

---

## 7. 黑产安全研究员 — "我现在连一个恶意 peer 都防不住"

实际发现的漏洞（6 个已修）：
- neural_share 消息在 swarm.js 中没路由（BUG）
- 旧 HTTP 服务器 /shutdown /api/chat 等零鉴权
- neural-mesh.js 权重数据无 NaN/Infinity/维度校验
- 文件路径穿越（peerId 未 sanitize）
- P2P 消息无签名验证
- 数据投毒攻击可污染全网权重

**修正：** 实际审查后发现 REST API v1 有 Bearer 认证、限流、Joi 校验、helmet 安全头。之前判断过严。已修复 3 个 Critical + 3 个 High。
