## 🎯 小步快跑原则 (最核心的原则)

这是 PeerTalk 最重要的开发原则。**核心思想**：**每一步都很小、每一步都很快、每一步都是完整可用的**。

### 一步的定义

一次代码改动应该满足以下条件：

```
✅ 只做一件事
   例：添加一个小功能、修复一个 Bug、改进一个函数

✅ 代码量不超过 500 行
   例：新增代码 < 500 行，修改代码 < 500 行

✅ 从分析到提交在 10-15 分钟内完成
   例：分析(1分钟) + 实现(5分钟) + 测试(3分钟) + 提交(1分钟)

✅ 改动完全自我包含
   例：不依赖其他未完成的改动

✅ 改动后系统仍然完全可用
   例：其他人能继续使用，不会受到影响
```

### 为什么要小步快跑

| 好处 | 详解 |
|------|------|
| **快速反馈** | 小改动容易测试，能马上知道是否正确 |
| **问题追踪** | 出问题时能快速定位是哪一步引入的 |
| **风险低** | 即使有问题，也只影响一个小功能 |
| **持续可用** | 系统任何时刻都是可用的，能随时上线 |
| **团队协作** | 其他人审查小改动更容易，冲突更少 |
| **心理舒适** | 频繁的小成功比偶尔的大成功更激励人 |

**总时间** ⏱️ **通常 10-20 分钟**

**关键**：整个流程 **100% 由 AI 自动执行**，不需要任何人工干预。

### 反面例子：什么是"太大的一步"

❌ **这些都是"太大的一步"，应该拆分**：

| 反面例子 | 为什么不好 | 应该怎样做 |
|---------|----------|----------|
| 一次改动 2000 行代码 | 难以审查和测试 | 拆分成 4 个 500 行的改动 |
| 同时做多个不相关的改进 | 出问题时难以定位 | 分别完成每个改进 |
| 改动后没有完整测试 | 无法确认改动是否正确 | 必须有测试验证 |
| 改动破坏了原有功能 | 严重的回归问题 | 必须运行回归测试 |
| 改动需要等待其他改动完成 | 产生依赖和耦合 | 确保改动完全独立 |

## 📝 版本控制规范

### AI 自动提交原则

AI 在以下情况自动创建新的 commit：

```
✅ 添加一个新功能
   条件：通过了所有测试和审查

✅ 修复一个 Bug
   条件：验证了修复有效

✅ 改进代码质量
   条件：确认改进有效

✅ 更新文档
   条件：内容准确有效
```

**核心原则**：每个 commit 必须是**完整、独立、可工作的**。AI 从不创建"半成品" commit。

### AI 自动审查机制

在提交前，AI 必须自动完成以下审查：

```
1️⃣ 代码质量审查
   确保代码符合质量标准（≥70分）

2️⃣ 功能正确性审查
   通过所有单元测试和集成测试

3️⃣ 安全审查
   检查是否有安全漏洞或违反安全策略

4️⃣ 兼容性审查
   确保改动不破坏已有功能

5️⃣ 文档审查
   确保有相应的文档说明
```

**关键**：这些审查 **100% 由 AI 自动完成**，不需要人工。

### 提交信息格式（由 AI 自动生成）

```
<type>: <brief description>

<detailed description generated by AI>
- 做了什么（AI 生成）
- 为什么要做（AI 分析）
- 影响范围（AI 分析）
- 测试覆盖（AI 验证）
- 性能影响（AI 测量）
```

**类型包括**：
```
feat       新功能
fix        Bug 修复
refactor   代码重构
perf       性能优化
test       测试相关
docs       文档更新
chore      日常维护
```

### 分支策略（AI 自动管理）

```
main 分支
├─ 生产代码
├─ 必须始终稳定可用
└─ 所有改动都通过验证才能合并

feature/xxx 分支
├─ 开发新功能
├─ 通过验证后自动合并到 main
└─ 自动删除

fix/xxx 分支
├─ 修复 Bug
├─ 通过验证后自动合并到 main
└─ 自动删除
```

**关键约束**：
- ✅ AI 自动执行代码审查
- ✅ 满足标准后自动合并
- ✅ **AI 有完整的合并权限，不需要等待任何人的批准**

## 🧪 测试驱动开发（100% AI 自动执行）

### AI 的自动测试权限

AI 有**完整的测试权限和决策权**：

```
✅ AI 自动编写单元测试
✅ AI 自动编写集成测试
✅ AI 自动编写对抗性测试
✅ AI 自动运行所有测试
✅ AI 自动分析测试结果
✅ AI 根据测试结果自动决定是否提交代码
```

### 测试覆盖要求（AI 自动验证）

```
✅ 新代码必须有相应的单元测试
   覆盖率 ≥ 90%

✅ 关键路径必须有集成测试
   例：核心业务流程、关键决策

✅ 所有改动必须通过全量回归测试
   确保没有破坏现有功能
```

### 测试内容（AI 自动设计）

| 测试类型 | 说明 | 例子 |
|---------|------|------|
| **正常场景** | 功能按预期工作 | 输入有效数据，得到正确输出 |
| **边界情况** | 极端输入值的表现 | 空输入、超大输入、零值 |
| **异常处理** | 错误情况的表现 | 无效输入、网络错误、超时 |
| **性能要求** | 执行时间是否可接受 | 单个操作 < 1s、批量操作 < 10s |
| **安全检查** | 是否有安全漏洞 | SQL 注入、XSS、权限绕过 |

### AI 的自动验证流程

```
1️⃣ AI 编写代码
   ↓
2️⃣ AI 自动生成测试用例
   ↓
3️⃣ AI 运行测试
   ├─ ✅ 通过 → 继续
   └─ ❌ 失败 → 自动修复代码或测试 → 重新运行
   ↓
4️⃣ AI 运行全量回归测试
   ├─ ✅ 通过 → 继续
   └─ ❌ 失败 → 自动修复 → 重新运行
   ↓
5️⃣ AI 分析测试覆盖率
   ├─ ✅ ≥ 90% → 继续
   └─ ❌ < 90% → 补充测试 → 重新运行
   ↓
6️⃣ AI 验证所有条件满足后自动提交
```

### 关键决策权

```
✅ AI 判断代码是否满足质量标准（无需人工审查）
✅ AI 判断测试是否充分（无需人工验证）
✅ AI 判断是否可以提交（无需人工批准）
✅ AI 有权自动拒绝不满足标准的代码，并自动改进直到满足
```

## 📊 代码质量标准（AI 自动评估和改进）

### 代码要满足的基本要求

```
✅ 按照命名规范命名
   • 变量：camelCase (例：myVariable)
   • 常量：UPPER_SNAKE_CASE (例：MAX_SIZE)
   • 类/接口：PascalCase (例：MyClass)

✅ 每个函数有清晰的注释说明用途
   • 函数功能描述
   • 参数说明
   • 返回值说明

✅ 错误处理完整，异常不能静默
   • 捕获异常后必须记录或处理
   • 不能忽略错误

✅ 没有硬编码的配置值
   • 所有配置通过环境变量或配置文件
   • 代码中只有常量定义

✅ 代码行长不超过 100 字符
   • 方便阅读和比较

✅ 复杂逻辑有中文注释解释思路
   • 算法注释
   • 业务逻辑注释
```

### 代码的四个质量等级

| 等级 | 分数 | 说明 | 是否可提交 |
|------|------|------|----------|
| **EXCELLENT** | ≥ 90 | 代码写得非常好，可以作为示范 | ✅ 优先提交 |
| **GOOD** | 70-89 | 代码质量很好，完全可以投入生产 | ✅ 可以提交 |
| **FAIR** | 50-69 | 代码能工作，但有改进的空间 | ❌ 需要改进 |
| **POOR** | < 50 | 代码质量较差，有明显问题 | ❌ 必须改进 |

### AI 的自动决策

```
📊 AI 自动评估代码质量
   ↓
如果分数 ≥ 70 分
   ✅ AI 可以直接提交

如果分数 < 70 分
   ❌ AI 必须改进代码直到 ≥ 70 分才能提交

关键原则：AI 从不提交低于 70 分的代码
          这是硬性要求
```

## 🔐 关键文件保护（AI 的自我约束）

### 保护清单

以下文件对系统至关重要，AI 必须特别谨慎：

```
🔴 超级关键文件（不能随意修改）
   .git/              - 版本控制系统
   bridge/src/        - 核心代码
   package.json       - 项目配置
   docs/              - 项目文档

🟡 关键文件（修改需要谨慎）
   .env               - 环境变量
   rules.md           - 系统规则
   config/            - 配置文件

🟢 普通文件（可以正常修改）
   src/               - 应用代码
   tests/             - 测试代码
   其他               - 其他文件
```

### 保护机制

```
对于🔴超级关键文件：
   ❌ 不能直接删除
   ❌ 不能删除超过 10% 的内容
   ❌ 不能修改关键部分
   ✅ 修改必须通过特殊审批流程
   ✅ 修改前必须备份
   ✅ 修改后必须验证

对于🟡关键文件：
   ✅ 可以修改
   ✅ 修改前询问用户
   ✅ 修改后进行验证
   ✅ 提交时详细说明原因

对于🟢普通文件：
   ✅ 可以正常修改
   ✅ 遵循普通的代码审查流程
```

## 💡 开发实践总结

| 原则 | 含义 | 实现方式 |
|------|------|---------|
| **小步快跑** | 每步 < 500 行，< 15分钟 | 严格控制改动范围和时间 |
| **自动优于手动** | 所有流程自动化 | 审查、测试、审批都由 AI 执行 |
| **持续可用** | 任何时刻系统都能用 | 每个改动都经过完整测试 |
| **快速反馈** | 立即知道改动是否正确 | 小改动容易测试和验证 |
| **版本可追踪** | 每个改动都有记录 | 完整的 Git 历史 |
| **质量保证** | 代码质量 ≥ 70 分 | AI 自动评估和改进 |
